## 1. 目标

按配套 PRD 交付一个最小但完整的用户闭环：

```text
浏览待回答问题 → 作者邀请回答者 → 回答者接受/婉拒
      → 接受者发布公开回答 → 邀请完成 → 作者收到通知并可采纳
```

本执行计划用于安排实现顺序和验收，不替代配套 PRD 中的字段、权限、业务规则及产品决策。

## 3. MVP 产品默认值

若产品负责人暂未修改配套 PRD 第 16 节的待确认项，本迭代采用以下默认值：

| 决策 | MVP 默认值 | 说明 |
|---|---|---|
| 接受邀请 | 显式接受/婉拒 | 打开通知只标已读，不等于接受 |
| 邀请有效期 | 7 天 | 到期时逻辑上失效；若需要物理更新，由任务/惰性过期方案决定 |
| 单次发送数 | 最多 5 人 | 0 人拒绝；超限整批拒绝，避免部分成功的歧义 |
| 每问题频控 | 每 24 小时最多邀请 5 个不同用户 | 重试同一幂等请求不重复消耗配额 |
| 每邀请者频控 | 每 24 小时最多发 20 条 | 服务端计数，避免多实例绕过 |
| 同一用户/问题 | 7 天内最多创建一次邀请 | 活跃邀请与历史终态均按创建时间计算 |
| 待回答定义 | 没有公开、审核通过、未删除的回答，且问题状态为 open | 隐藏或删除的回答不算有效回答 |
| 接受/婉拒通知 | 通知问题作者 | 尊重现有通知偏好；不发邮件或推送 |
| 候选人规则 | 同话题公开回答和话题关注的确定性排序 | 不使用私信、邮箱或敏感画像 |

调整这些默认值需同步修改 PRD 和测试场景，避免文档、接口和实现三处不一致。

## 4. 任务拆分与顺序

### 阶段 A：后端数据与待回答发现

**BE-01 邀请数据模型与迁移**

- 新增邀请状态常量、数据库模型、迁移和 DAO 接口。
- 建立问题、邀请对象、状态和时间的必要索引。
- 对同一问题和接收者的活跃邀请施加数据库级并发保护；不能只靠应用层先查后插。
- 迁移需可从空库和当前已迁移数据库顺序执行，遵循现有迁移器事务/版本约定。

**完成证据**：迁移链集成测试通过；唯一性/并发约束测试通过；不存在外键或索引策略与项目 ID/删除语义冲突。

**BE-02 待回答公开列表**

- 增加 `GET /questions/unanswered`，支持话题筛选、排序、cursor 和 limit。
- 复用统一问题可见性条件、有效作者条件、公开回答可见性条件。
- 稳定排序键建议为 `(create_time, question_id)`；如提供最久未回答排序，明确其排序键和相同时间 tie-break。
- 游标绑定列表类型、排序、话题过滤及版本；错误游标返回统一参数错误。
- 查询需取 `limit+1` 个有效问题确定 `has_more`，不得在可见性过滤前截断导致假空页。

**完成证据**：隐藏父问题、禁用作者、待审/隔离问题不泄露；公开有效回答会排除问题；跨页无重复/遗漏；筛选条件改变后的旧游标拒绝。

### 阶段 B：候选和邀请状态机

**BE-03 候选回答者接口**

- 增加作者专属候选接口，使用公开用户名搜索和确定性相关度。
- 排除提问者本人、禁用账号、邀请接收关闭者、屏蔽/拉黑双方、已有活跃邀请者。
- 只返回所需公开字段和粗粒度推荐理由；不回传邮箱、隐藏作品或精确私人行为数据。

**BE-04 邀请创建事务**

- 校验作者权限、问题可见性/open 状态、没有公开有效回答、批次大小、频控、重复邀请和幂等键。
- 在事务中锁定必要事实行，写邀请、通知、审计；任何一步失败整批回滚。
- 响应提供逐个邀请结果或采用整批原子失败，最终契约只选择一种；MVP 推荐整批原子失败。

**BE-05 收件箱、接受和婉拒**

- 增加 `GET /me/answer-invitations` 与接受/婉拒接口。
- 状态转换：`pending → accepted | declined`；重复同一操作幂等，竞争状态返回冲突。
- 操作者必须是接收者；发起者、其他用户、管理员不得代替接收者操作。
- 操作时复核邀请、问题、双方账号和屏蔽状态；问题失效时返回安全错误并确保邀请不能继续接受。

**BE-06 回答完成和失效联动**

- 仅当被邀请者的回答最终通过审核且公开时，更新对应 `accepted → answered`。
- 问题关闭/解决/下架、任一方禁用或建立屏蔽关系后，未处理邀请转为失效或在读时惰性失效；选择一种一致策略并测试。
- 自动联动需原事务写入，或经事务 outbox；消费者必须幂等且有失败重试/补偿路径。

**完成证据**：真实 MySQL 集成测试覆盖迁移、并发邀请、频控并发、接受/婉拒竞争、接受/撤回竞争、审核通过联动、状态失效和通知原子性。

### 阶段 C：前端发现与邀请操作

**FE-01 待回答发现页**

- 新增路由和 API 类型，动态 `/questions/:id` 路由冲突已检查。
- 实现话题筛选、排序、URL 同步、cursor 加载更多和浏览器前进/后退。
- 实现加载、空、错误重试、无更多状态；筛选快速切换时取消或忽略过期响应。

**FE-02 问题详情邀请选择器**

- 只对满足资格的本人问题显示入口。
- 实现候选加载、公开推荐理由、多选上限、频控/冲突错误和防重复提交。
- 成功后显示邀请状态；不暴露其他被邀请者名单。

**FE-03 通知中心和邀请处理**

- 增加通知类型映射、文案和安全跳转。
- 接受/婉拒与已读状态分离；操作完成刷新邀请状态和未读数。
- 问题不可见时渲染安全占位，不能从通知缓存或旧链接泄露标题正文。

**FE-04 移动端**

- 375px 验收发现页筛选、问题条目、邀请对话框、长列表滚动和固定操作区。
- 键盘焦点、Escape 关闭、提交中禁用和窄屏文字换行正常。

**完成证据**：前端 build 通过；Playwright 覆盖主要正向流程、权限拒绝、超限、失败重试和 375px 视口。

### 阶段 D：灰度与数据观察

- 增加服务端功能开关，默认关闭；紧急情况下可统一关闭候选与发邀请入口。
- 只采集 PRD 定义的必要事件；邀请和内容事实仍以数据库为准。
- 准备首答时间、7 日首答率、邀请接受率、邀请完成率和投诉率的基线报表。
- 小流量灰度 7 天；根据实际基线设目标，不预先承诺增长百分比。
- 出现越权、内容泄露、明显骚扰或通知重复时，立即关闭开关并回滚/修复。

## 5. API 交付顺序

建议接口契约冻结后再并行前后端：

1. `GET /questions/unanswered?topic_id=&sort=&cursor=&limit=`
2. `GET /questions/:id/invitation-candidates?q=&cursor=&limit=`
3. `POST /questions/:id/answer-invitations`
4. `GET /me/answer-invitations?status=&cursor=&limit=`
5. `POST /answer-invitations/:id/accept`
6. `POST /answer-invitations/:id/decline`
7. P1 再增加邀请历史管理/撤回接口。

所有响应复用项目统一 envelope；ID 字符串化；limit 默认 20、上限 50；错误码和 HTTP 状态以仓库现行契约为准。

## 7. 风险与实现注意事项

- **可见性规则重复**：候选、列表、详情和通知各自手写条件容易遗漏。优先复用统一可见性 SQL/DAO；复用困难时先补共享入口。
- **频控并发超额**：简单 `COUNT` 后插入在并发下会超限。使用原子配额、锁定维度行或可证明串行化的数据库事务方案，并有 MySQL 并发测试。
- **审核异步联动遗漏**：不能把“回答创建成功”当作“邀请已回答”；必须以审核通过公开为准。
- **候选排序成本**：候选计算采用可索引查询与上限；避免对全体用户逐个 N+1 统计。
- **通知目标失效**：通知只是入口，读取和操作 API 都必须复核访问权。
- **旧基线风险**：此文写作时远端不可达；不要直接把旧 PRD 工作树合入当前主线。先比较提交图，再挑选文档或代码变更。
